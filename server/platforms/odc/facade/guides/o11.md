# SSAM: the O11 lane (Service Studio)

Every step is an MCP call. A refusal carries `continuation: {tool, arguments, why}`; follow it. `ssam://guide/refusals` lists every code.

## Connect

1. The person opens the Service Studio normally (Start menu), signs in and opens the module. Nothing is copied into the Studio folder.
2. `ssam_connect {lane:"o11", dryRun:true}`: the static compatibility check only; nothing is sent to the Studio.
3. `ssam_connect {lane:"o11"}`: attaches the bridge in memory. The answer shows `compat`, `bridges` and `selftest.unavailable`.
4. `o11_studio {command:"status"}`: the Studio, the active module, pending dialogs.

Never ask the person to save, publish, close or restart to connect. With several Studios open, pass `pid`.

## Read an application

1. `ssam_map {lane:"o11", target}`: every element of the capture with its `@key`, kind, role, parent and path; paged and filtered.
2. `o11_inspect {oml, path:"@<key>", expectedSourceSha256}`: subtree, properties and usages of one element of the same capture. `select` reads several paths in one call; `usages:true` lists incoming references.
3. `o11_studio {command:"snapshot", args:{module}}`: a fresh capture of the open module when the map is stale.
4. `ssam_code {lane:"o11", action, part}`: the module as code, one word to read and write: part `ddl` (data as SQL DDL), `logic` (actions as pseudocode), `html` (screens). `grammar` gives the syntax and a from-scratch example (an empty module starts there), `read` the part with its keys, `check` validates against a capture without Studio, `write` delivers it through `o11_deliver`; `files` sends several code files in the same check or write.

## Express a change

1. `ssam_discover {intent, lane:"o11"}`: the capabilities the intent names, with the exact operation, contract, proven example, bindings, limits and the next call.
2. `ssam_reference {lane:"o11", kind, query}`: `api`, `functions`, `ui-block`, `types`, `where-can`, `recipe`, `check-job`, `check-delivery`, `verify-message`, `example`, `rules` (the team rules before generating or changing modules: `query:"all"`; the 35 rules: `query:"padroes"`).
3. Write the job and deliver it (below). Only when the person asks for a headless proof: `ssam_job {lane:"o11", job}` or `o11_job {job, captureProducers}` on a fixture; a failed run answers with `discovery` (contract of the failing op and the next step). Nothing reaches the Studio there.

When you fall back to native verbs because the compact form does not cover the case, record it with `ssam_friction {view:"report", kind:"gap"}`.

Jobs: write them with Write (UTF-8) to a file and pass the path; never a heredoc.

## Deliver

To change only a few lines of a read action, use `ssam_code {lane:"o11", action:"write", module, part:"logic", element:"X", basedOn:"<textSha>", edits:[{replace:"@n4", with:"..."}]}`. Take `basedOn` from the action read; edits address that read and keep its other lines. Use `also:[{part:"logic", element, basedOn, edits}]` for more actions in the same delivery.

For 6 or more elements, call `ssam_code {lane:"o11", action:"plan", module, items:[{kind, name, intent, signature}]}`: write its shared data first, launch its batch prompts in parallel, then send its `final` write.

With subagents, each writes its part to its own UTF-8 file: `.flow` may hold several actions, each with its `///` description and header at column 0, with a blank line between; data goes in `.ddl`, screens in `.html`, and JSON ops in `.json`. Before answering only the absolute path, each runs `ssam_code {lane:"o11", action:"check", module, files:["C:\\...\\shared.ddl", "C:\\...\\shared.json", "C:\\...\\parte-1.flow"]}` until ok; checks use the newest capture, never contact the Studio and are safe in parallel. If this part calls an action from another part, include that file in the check too. The main agent sends ONE `ssam_code {lane, action:"write", module, files:["C:\\...\\parte-1.flow", ...]}`, never copying their text into the call. SSAM splits the actions and names every problem by file (`files/<i>`) in one refusal.

`o11_deliver {module, job, checks, authorize}` with the user's own words, directly: a fresh capture of the module as it is now in the Service Studio, headless validation (TrueChange), one native merge and the checks, in one call that refuses before any change. `module` may be a label with spaces ("GameStore CS" reaches the open GameStore_CS). `until:"apply"` validates without merging, only when the person asks. A refused preflight returns every problem at once (`PREFLIGHT_REFUSED`, `problems`): fix them all with one `patch` + `basedOn` (`nextBasedOn` of the answer; paths may name elements, `actions/<Action>/steps/<as>/...`, as each `patchByName` does), or send in `job` only the changed actions with the same `basedOn` (a partial job); never the whole job again. Producers named by `reference` ops are captured read-only by name; no `--producer` file is needed. Never repeat an uncertain merge; read its receipts first (`ssam_task {id}`); a merge the Studio rolled back is proven and closed by the delivery itself (`MERGE_ROLLED_BACK`, the module is free), and `ssam_task {id, close:{reason}}` closes an uncertain task only with the proof that nothing was applied. A data model the SQL Server upgrade would refuse (two Delete cascade paths to one table, a cascade cycle) is refused before the merge, with one line per reference to change in `refusalLines`. Defaults the Studio drops on elements a merge creates are merged in a second native merge of the same call (a Studio whose bridge predates it is refused before the merge: `BRIDGE_OUTDATED`); if one is still lost, the answer names it in `mergeOrder` with its repair job as the continuation.

Publishing: `o11_deliver {..., publish:true}` publishes the same module right after a clean merge, in the same call and with the same words (`result:"delivered and published"`, `publish:{outcome, ...}`). A merge that is not clean skips it (`publish.outcome:"skipped"`); a failed or uncertain publication answers `result:"delivered"`, `PUBLISH_FAILED` or `PUBLISH_UNCERTAIN` and only the `o11_publish` continuation: the delivery is never repeated. `o11_publish {module, authorize}` publishes alone (`consumers:true` then refreshes and publishes every consumer). When the person grants it once in their own words, naming the app, `ssam_grant {action:"grant", lane:"o11", app, modules?, verbs?, words}` records a standing grant; `o11_deliver` and `o11_publish` without `authorize` then use it and answer `authorization:{source:"standing-grant", grantId}`. `ssam_grant {action:"revoke"|"list"}` revokes or lists them; never create a grant the person did not ask for.

## HTML prototype → native screens

A prototype folder (index.html, app.js, styles.css, mock data, icons, images), or the .zip it came in, becomes native screens in ONE call, with no reading and no conversion by the model:

`o11_deliver {module:"<open module>", job:{ops:[{op:"prototype", data:{source:"<prototype folder or its .zip, absolute path>"}}]}, publish:true, authorize:"<the owner's words>"}`

- Give a .zip as it is (SSAM extracts it safely once; never unzip it with a shell). Do not read `app.js`, `model.js`, `styles.css`, the `.jsx` or the HTML, and never split the views into several calls: SSAM renders the prototype headless, finds every view, modal, the shared shell, the mock data and the events, and builds one screen per view in a flow of its own (`<Prefix>`), a shell block, native popups, entities with the mock data, aggregates and server actions, with the prototype CSS verbatim in a theme of its own. MainFlow, the module theme and the other screens are never touched; a name already taken by an element the import does not own becomes `<Prefix><Name>` (listed in `renamedFrom`), never a refusal.
- A prototype with several versions (`v1`/`v2`/`v3` `.jsx`, a design canvas): SSAM builds the one the HTML opens and lists the others in `prototype.source.unreferenced`; another version only when the person asks for it (`data.mapping.version:"<file of the folder>"`).
- Several `.html` pages at the root and no `index.html` (the app and a style guide): the refusal names in its patch the page that runs the app, already captured with it (`verified`); send the `correctedJob` (the capture is reused), or give `data.entry` in the first call. Reference images (`screens/*.png`) are never part of the app.
- The owner's words in `authorize` cover the import, the publication and the demo data: after a clean publication the mock rows are written into the empty regular entities the import created (Edit Data of this Studio). `data.seed:false` leaves the data out.
- A refusal of the prototype (`PROTOTYPE_SOURCE_INVALID`, `PROTOTYPE_RENDER_FAILED`, `PROTOTYPE_AMBIGUOUS`, `PROTOTYPE_NAME_COLLISION`, `PROTOTYPE_BINDING_REQUIRED`; `PROTOTYPE_IR_INVALID` is an SSAM defect) comes ONCE, before any Studio work, with every problem, the ready `patch` over `/ops/<i>/data` and `correctedJob`: send the patch as it is (`patch` + `basedOn`). `data.mapping` only when a refusal asks for it.
- Screens on real data (the published actions of a producer module, never mock entities): `data.bind {producer:"<Module>"}` in the same call. The answer `PROTOTYPE_BINDING_REQUIRED` proposes, at once, the source of each screen and popup (a Data Action calling the producer's action), each list (an output list), each text (an expression over the outputs, the prototype's own words kept), each event (`call` of a producer action with `then: ["refresh <source>", "message <text>", "download"]`, or `navigate`); every proposal was planned and built offline against the producer before it was offered. Apply the whole `patch` as it is; an item marked unresolved has no patch: write it (`bind.slots["<k>"]: "<expression>"`) or `null` to keep the prototype's value. A bound collection gets no entity and no seed; the delivery references the producer's elements it uses.
- A build problem on a generated item is the SSAM's: the delivery rebuilds once without it (`prototype.degraded`); a second failure is `VALIDATION_REFUSED` with `ssamDefect:true` and the ready `mapping.ignore` patch.
- The answer carries the receipt in `prototype`: screens (with `url`), popups, blocks, resources, data, events, fidelity per explored state, Verify warnings, seed and timings. Give the person the screen links.
- A rehearsal without merge only when the person asks: `until:"apply"` (no publication, no data).

## The Studio

`o11_studio {command, args}` with `command` one of `status`, `wait`, `open-module`, `snapshot`, `errors`, `publish-log`, `windows`, `dismiss-dialog`, `login`, `refresh-references`.

- `o11_studio {command:"wait", args:{condition:"idle"}}` waits instead of a sleep loop; conditions `idle`, `no-dialogs`, `open` (with `module`), `signed-in` (with `host`). `idle` also waits for a running server operation (a publish the person started) and for a running SSAM write.
- `o11_studio {command:"open-module", args:{name}}` resolves the name by the environment inventory; an unknown name is refused at once with `MODULE_NOT_FOUND` and `suggestions`.
- `o11_studio {command:"refresh-references", args:{module?, producers?}}` runs the Studio's own Refresh References (one Studio command, Ctrl+Z undoes it); it never adds an element. With `add:[{producer, elements}]` and/or `published:true` it runs the Studio's own Manage Dependencies: new elements of any producer (eSpace, Extension, (System)) from its published signature, each named producer brought to it, one Studio command, all or nothing. `o11_deliver` runs it by itself before its merge: never ask the person to click Manage Dependencies.
- `o11_studio {command:"login", args:{host}}` uses the Studio's own sign-in dialog.
- `o11_studio {command:"publish-log", args:{module?}}` reads only this Studio's 1-Click Publish tabs (the person, `o11_publish`, `o11_deliver` publish). A publication made elsewhere is a module version in Service Center: the answer's `elsewhere` is `o11_service_center_read {action:"versions", moduleKey}`.

## Dialogs

- An owned window: `o11_studio {command:"windows"}` reads it; `o11_studio {command:"dismiss-dialog", args:{title}}` closes it like its X (Cancel), only if the person agrees.
- A web dialog (recovery Open | Discard, Manage Dependencies, others): the bridge cannot answer it. Ask the person to answer it in the Studio, then `o11_studio {command:"wait", args:{condition:"no-dialogs"}}` and repeat the call.
- A merge editor left open: the person finishes or cancels it in the Studio.
- Never restart the Studio because of a dialog.

## Environment, data and Service Center

- `o11_environment {action, host, ...}`: `inventory`, `download`, `download-app`, `templates`, `create-app`, `add-modules`, `create-module`, `update-app`, `refresh-refs`, `set-user-provider`, `delete-app`. Always through the connected Studio's session. Writes need the user's words; `delete-app` uses the same engine as the Service Center delete below: the words name the app and every consumer. `refresh-refs {module, publish:true}` publishes through the environment session, not the Studio tab: its `publication {version, at, operationId}` is the new module version in Service Center, never in `publish-log`, and the module open in the Studio stays on the version it was opened at.
- `o11_data {host, module, oml, request}`: published entity records through the Studio's Edit Data. Writes need the user's words and a stable `operationId`. File loads use `files:[absolute paths]` (JSON, JSONL, CSV) and REQUIRE `keys` (unique, non-null natural keys), with `columns`, `references` and `dryRun` (per row: insert, update current -> new, unchanged). Equal rows skip and missing rows insert (an update with `insertMissing:false` refuses absent keys); a key that exists with other values is an overwrite: the call stops before any write with `updatePreview` and writes only with `confirmUpdates {previewSha256, authorize}` carrying the owner's next message, which states that row count. One refusal before any write; the same `operationId` resumes by re-reading the keys (the load's words come from its plan). `close {preview:true}`, then `close {previewSha256, authorize}` with the owner's words stating the rows left unwritten.
- `o11_service_center_session`, `o11_service_center_read`, `o11_service_center_write`: Service Center through the Studio session first, then the vault. A missing credential: `ssam_credentials {action:"prompt", kind:"o11-service-center", host}`.
- `o11_service_center_write {action:"delete", host, applications|modules|extensions|prefix}`: the preview (checks consumers and the server's own simulation; the exact list with its count, the modules that go and the backup plan, a `confirmationToken`; nothing sent). Then `{action:"delete", host, confirmationToken, words}` with the owner's reply after the list: deletes in order, answers deleted/uncertain/notStarted by name, or DELETE_REFUSED with every problem and its fix. module-delete, extension-delete, application-delete, solution-delete and db-connection-delete take the same two calls.
- `o11_extension {action:"read"|"publish"|"delete", host, extension, spec}`: a .NET extension without Integration Studio, built here and published through the Studio's session; read first to get the current spec; publish answers created/updated/already-running; delete previews first and executes with `confirmationToken`.
- Every delete takes two calls (CX15): without `confirmationToken` it only shows the list; show the owner that EXACT list and ask; the owner's reply, verbatim, states the number of items and names the targets; words said before the preview never confirm it. The words are the owner's next message after the list, copied whole: never write, complete, translate or reuse words yourself (not the request, not a template, not a reply to another list); without such a message, ask the owner and stop. Interrupted, CANCELLED, SC_LOCAL_FAILURE or another local failure, 'rejected' or no answer: read ssam_task {id:<operationId from the preview>} before telling the owner anything; never say nothing happened without it.
- Job ops `rest`, `rest-expose` and `soap` (O11 only) through o11_deliver; the contracts come from ssam_discover.
- `o11_access {action:"plan", manifestPath}` then `{action:"apply", manifestPath, words}`: end-user roles by manifest. It never creates user accounts: the person creates them in Users or Service Center.
- `o11_dependencies {action, ...}`: producers, captures and inspection of dependencies.

## App session

`context`, `propose`, `continue` and `status` run the controlled app session of the O11 lane in this same server.

## Debugger

`ssam_debug {lane:"o11", ...}`: headless server debugger. The credential comes from the Studio session or from `ssam_credentials {action:"prompt", kind:"o11-debugger", host}`; never a file and never an argument.

## Refusals of this lane

| code | next call |
|---|---|
| `STUDIO_NOT_CONNECTED` | `ssam_connect {lane:"o11"}` |
| `INCOMPATIBLE_STUDIO` | `ssam_doctor {lane:"o11", checks:["compat"]}` |
| `DIALOG_OPEN` | `o11_studio {command:"dismiss-dialog", args:{title}}` or the person in the Studio |
| `DIALOG_RECOVERY`, `DIALOG_MANAGE_DEPENDENCIES`, `DIALOG_MERGE_EDITOR`, `DIALOG_WEB` | the person answers in the Studio, then `o11_studio {command:"wait", args:{condition:"no-dialogs"}}` |
| `O11_SC_SECRET_NOT_FOUND` | `ssam_credentials {action:"prompt", kind:"o11-service-center", host}` |
| `O11_STUDIO_OPERATION_UNAVAILABLE` | `o11_environment {action:"inventory", host}` |
| `MODULE_AMBIGUOUS` | `o11_deliver` again with one of `candidates`, the exact module name |
| `MODULE_NOT_FOUND` | `o11_studio {command:"open-module", args:{name}}` with one of `suggestions` |
| `PREFLIGHT_REFUSED` | `o11_deliver {patch, basedOn:{job, sha256}}` fixing every item of `problems` (paths by name as in `patchByName`), or `{job: <only the changed actions>, basedOn}` |
| `MERGE_ROLLED_BACK` | `o11_deliver` with the corrected job: nothing was applied and the module is free |
| `VERIFY_UNAVAILABLE` | `o11_studio {command:"errors"}` once the Studio is idle; the merge is kept for review |
| `PUBLISH_FAILED`, `PUBLISH_UNCERTAIN` | `o11_publish {module}` only; never repeat the delivery |
| `STUDIO_BUSY_TIMEOUT` | `o11_studio {command:"wait", args:{condition:"idle"}}`, then `o11_publish` again |
| `O11_PRODUCER_CAPTURE` | `ssam_job {lane:"o11", job, captureProducers}`: the runner captures the producer signature read-only through the signed-in Studio and binds it to the job |
| `COMPONENT_MISSING` | `ssam_doctor {lane:"o11"}`; reinstall or update, nothing is built here |
