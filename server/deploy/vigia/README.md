# Automatic Studio watcher

Development checkouts support tests and `--dry-run` only. Dry runs read local metadata and official public sources; they never read the vault or contact deployment endpoints.

## Execution account and clone

Activate only an owner-reviewed release in a dedicated Windows account's own clone, named `vigia-run`, on `server/vigia-run`. `.git` must be a directory owned by that account. Shared worktrees, foreign owners, reparse points, alternate object stores, writable foreign ACL entries and executable/included Git configuration are refused. Provision restrictive ACLs before activation. The private item and its whole tree accept no write by another account, including an inheritable ACE that later descendants would receive. Ancestors (C:\ included, left at its Windows default) are refused only for an untrusted owner or a right that can replace the child: Delete, DeleteSubdirectoriesAndFiles, ChangePermissions, TakeOwnership or GENERIC_ALL; their inherit-only ACEs do not apply to them.

Copy `config.example.json` to `C:\ssam-priv\vigia\config.json`. Set the exact HTTPS `trustedRemote`, `bridgeMode` (see Bridge mode), agent release commit/ref, the published agent packs (`agentPack`, `agentPackByRuntime`), `maxWindow`, baseline bundle pins and deployment destinations. Automatic output, bundle, installer, temporary, configuration, vault and ODC features (`featuresRoot`) paths must be private under `C:\ssam-priv\`. Never activate the development worktree.

Updates fetch main from the fixed remote and fast-forward. Watcher Git calls disable hooks, fsmonitor, external diffs, credential helpers, external/file transports and global/system configuration. Automatic mode requires `ownerSigningPublicKey`, and fetched/executed commits must pass `git verify-commit`. The only alternative is the owner's explicit `acceptUnsignedMain:true` in private configuration; every round then sends the `unsigned-main` notification (toast, optional webhook and the VPS journal through `logger -t ssam-vigia`). No key is invented.

In `signed-offers` bridge mode, keep the Authenticode key nonexportable in the dedicated account; `server-only` needs no certificate (`set-secrets.ps1` takes Enter for the thumbprint, and a value given must be 40 hexadecimal characters). Use an unpackaged PowerShell terminal for vault setup; `Windows.ApplicationModel.Package.Current` detects packaged execution. `set-secrets.ps1` provisions a new vault without replacing an existing one, so a thumbprint cannot be added later: a server-only vault that must one day move to `signed-offers` is recreated, which generates a new Ed25519 manifest key that the agents pin. `initialize-journal-key.ps1 -Vault <private path>` adds only a DPAPI-protected random HMAC key to an existing schema-2 vault, preserving the other encrypted values. These are owner actions, never development-test operations.

`attempt.json`, `release.json` and `deployment.json` use HMAC-SHA256 bound to their absolute paths. Invalid, relocated and unsigned journals stop the round; they are never silently migrated.

## Where new Studios are learned (`sources.mjs`)

The latest released Studios come only from OutSystems' public pages, read anonymously each round. Service Studio (version with build, file names and sizes for Windows, Mac Intel and Mac ARM) comes from the outsystems.com/downloads screen service `DataActionGetReleases`. ODC Studio's `X.Y.Z` and "Released on" day D come from the ODC Studio release notes on success.outsystems.com. The screen services' `apiVersion` tokens are re-read from the sites' published scripts every round (one more re-read when a token rotates mid-round). Only versions those pages name are probed: an unannounced version that already sits on releaseshub (11.55.96.65382 on 2026-11-09) is never asked about or offered. `releaseshub/v1/latest` is not used (it echoes the version it is asked about).

### The ODC build rule

Every version of the notes above the newest one the window serves (at most 3 per round: the highest and the oldest above the newest served; those in between are named once in `SSAM: Studio versions waiting to be read` and read after the older ones are served, so none is lost) is decided on its own, once, and the decision is kept in `studio-sources.json` in outDir:

- eligible builds were uploaded (CloudFront Last-Modified, read from `dxejw4oyledi.cloudfront.net` only) between D-1 00:00Z and the cutoff D+1 16:00Z; the decision is the highest eligible build, taken **only at the cutoff**. Until then the version is `pending` and nothing is offered: a next-day GA can come at any time up to the cutoff, and a decision is permanent;
- why these numbers (live uploads of 1.7.27 to 1.7.32, hours after D 00:00Z): the shipped builds were uploaded at 9.1 to 16.7 h and one next-day build at 32.75 h (1.7.28.10873); the first late hotfix came at 48.5 h (1.7.29.10953); the latest release candidate excluded by D-1 came 53 h before D (1.7.32.11059). 40 h is about the midpoint of 32.75 and 48.5. The day is read as UTC (the notes give no zone): both bounds leave more than half a day either way;
- assumption: within a version the GA has the highest build number (true for every version observed); a release candidate uploaded on D-1 with a higher number than the GA would be chosen;
- each decision records the build's distance to D and to the cutoff, and every upload seen, so drift shows;
- uploads after the cutoff or after the decision are never offered; the owner gets `SSAM: later Studio build not offered` once per build, with the `-Pin` line to serve it instead. When the version was not watched within 6 h before its cutoff (the watcher was stopped, or the file was deleted) and such an upload sits above the eligible build, it may be a re-upload of the GA: nothing is decided (`STUDIO_BUILD_AMBIGUOUS`) and the owner pins the build;
- versions are offered oldest first: a decided version waits (`queued`) while an older unserved one is pending or offered, so a version that ships one day after another is not skipped;
- an older unserved version left without a decision holds the newer decided ones back too, so it is never passed over unseen:
  - a source failure for it (`STUDIO_SOURCE_UNREACHABLE`, `_BLOCKED`, `_RATE_LIMITED`, `_CHANGED`, `_UNTRUSTED`) holds them with **no time limit**: it says nothing about the version, and the queue moves by itself once the source reads again. Holding is reversible, skipping is not;
  - an answer that needs the owner (`STUDIO_BUILD_AMBIGUOUS`, `STUDIO_BUILD_NOT_FOUND`) holds them for 48 h (`ODC_RULE.holdHours`) counted from the later of the newer version's cutoff and the first round that saw the hold (`holds` in `studio-sources.json`, persisted). A watcher that was stopped past the cutoff, or a `-Pin` of the newer version first, therefore still gives the owner the whole 48 h; nothing is ever skipped in the round that first sees the hold;
  - during a hold the owner gets `SSAM: Studio release needs the owner` once a day, naming both versions, the end of the hold (or "no time limit") and the full `-Pin X.Y.Z.<build>` and `-Skip X.Y.Z` lines of the older one;
  - when a limited hold ends the newer version is offered, the older one is recorded as skipped (`skipped` in `studio-sources.json`) and the owner gets `SSAM: Studio version skipped` once. A skipped version is no longer read, so a version not read this round (beyond the 3) is read next and served before the newer one: a decided version is never offered past an older version that was not read. Nothing ever serves a version older than the newest served;
- a decided version whose notes section changes is searched again for later uploads; if that search fails (a 503, a deadline), the decided build is still offered as it is and the search runs again the next round (the change is not taken as seen).

Load (probes are releaseshub `content` GETs; offline counts in RESULTADO-R3.md):

- decided and its notes section unchanged: 0 probes;
- first search of a version: up to 3 windows of 600 builds (at most 1,803) from the highest decided build or the last known GA (`ODC_KNOWN`), never from the Studio installed on the watcher machine (it may be a preview);
- pending, with builds found: one window of 100 above the last find per round (101); with nothing found yet: one window of 600 from the floor per round (601);
- past the cutoff without a decision (`STUDIO_BUILD_NOT_FOUND`, `STUDIO_BUILD_AMBIGUOUS`): one search a day, or at once when the version's notes change; the owner gets a daily notice that says what to run.

### Owner commands and recovery

- `vigia.ps1 -Config <config> -Pin X.Y.Z.B`: decides X.Y.Z as build B (it must exist on releaseshub; one GET and one HEAD), replacing any earlier decision. The version must have been read from the notes by a round. A window that already serves X.Y.Z keeps its image. It warns (and still pins) when B was uploaded more than 72 h before D-1 00:00Z or after the cutoff (`ODC_RULE.pinFarHours`), when releaseshub gives no upload time, or when B is below the highest build of an older version.
- `-Pin` of a version older than the newest one the window serves (typically one skipped after its hold) **has no effect**: it is recorded, the command answers `pinned-no-effect` and says so plainly, and nothing is offered, because no version older than the newest served is ever served again. To serve such a version, the window itself must change (a reviewed edit of `versions.json`), not the watcher. `-Pin` of a skipped version the window does not serve yet undoes the skip, and warns to approve it before the version it was skipped for. `-Pin` of a newer version warns about each older version still without a decision (it waits behind it, and when that one is skipped).
- `-Pin` and `-Skip` judge against the window the last round judged against (`served` in `studio-sources.json`: the production manifest in an automatic round), else the workspace `versions.json`; the answer names which.
- `vigia.ps1 -Config <config> -Skip X.Y.Z`: goes on without X.Y.Z at once (recorded as skipped by the owner: no longer read, holds nothing, never offered). It is how the owner releases a queue held behind a failing source or an unresolved version before the hold ends. `-Pin X.Y.Z.B` or `-Redecide X.Y.Z` undoes it. A version the window already serves (or older) is not skipped (`skip-no-effect`).
- One owner command per run: `-Approve`, `-Reject`, `-Retry`, `-SeedFeatures`, `-Pin`, `-Redecide` and `-Skip` cannot be combined with each other, with `-DryRun`, with `-AcknowledgeRollback` or with the internal `--round`, and none may be given twice.
- `vigia.ps1 -Config <config> -Redecide X.Y.Z`: drops the record of X.Y.Z; the next round searches it as never seen (past its cutoff an ambiguous answer then waits for `-Pin`).
- All three take the watcher lock and write the file back as the same signed journal (an automatic configuration never writes it unsigned).
- A `studio-sources.json` that cannot be read (tampered, truncated) stops the ODC lane only, with `STUDIO_SOURCE_STATE` and the notice `SSAM: Studio release needs the owner`. It does not heal by itself: rename or delete the file, and the next round decides again from the public pages (a version past its cutoff may then need `-Pin`).
- Service Studio keeps only a disposable cache (`studio-sources-o11.json`: the version and size last checked on releaseshub, so the same answer needs no probe); an unreadable one is ignored.
- A dry run reads both and writes nothing; without the journal key it reads the ODC decisions unverified (it acts on nothing).

### What the window does with it

It is judged against the served window (`manifest`), never against the Studio installed on the watcher machine: a release older than the newest served is `older-than-served` (logged, nothing offered); a newer Studio installed on the watcher machine (a preview) changes nothing and gives `SSAM: watcher Studio newer than the public release` once.

### Hosts, limits and errors

Discovery reads `api.outsystems.com`, `dxejw4oyledi.cloudfront.net`, `www.outsystems.com` and `success.outsystems.com` only, https, no redirect followed. A download touches only `api.outsystems.com` and `dxejw4oyledi.cloudfront.net` (`DOWNLOAD_HOSTS`; the other two also host user uploads), each URL and every redirect at the exact path of that release's Windows file (the releaseshub `content` link, then `/repository/<component>/<full version>/<file>`), no query, then size-checked against the source and the custody below. Answers are capped while they stream (8 MiB for scripts, 4 MiB for screen-service JSON). Each request has a 30 s timeout and 3 tries, all inside a 15 min deadline per lane (both lanes stay under 30 min, well inside the 2 h round period).

A source that cannot be read is `unavailable` with one of these codes:

- `STUDIO_SOURCE_UNREACHABLE`: network, 5xx or the deadline;
- `STUDIO_SOURCE_BLOCKED`: HTTP 403, a firewall or access rule;
- `STUDIO_SOURCE_RATE_LIMITED`: HTTP 429 after retries;
- `STUDIO_SOURCE_CHANGED`: a page changed shape;
- `STUDIO_SOURCE_UNTRUSTED`: an unlisted host (the notice names the host only);
- `STUDIO_BUILD_NOT_FOUND`, `STUDIO_BUILD_AMBIGUOUS` or `STUDIO_SOURCE_STATE`: see above.

That lane (or version) keeps its installed Studio for the round, and the owner gets a notice once a day per lane, version and code, with server text reduced to plain characters. It is `SSAM: Studio release source unreadable` ("retries next round") for what heals by itself, and `SSAM: Studio release needs the owner` (the command to run) for what does not.

## Installer and bridge custody

Candidates always come from verified installers downloaded from exact allowlisted hosts. The main-reviewed `publisher-pins.json` pins the OutSystems subject and CA. There is no installed-Studio fallback. Internal unsigned files inherit installer trust; any signature present must be valid. Unpinned installers stop the lane and notify the owner.

Installer hash, signer and the extracted content tree travel with the release and `/app/studio-provenance.json`; an image label records the metadata hash. Custody is checked before bundles, tests, bridge builds, image context and resume. Baseline companion bundles need a reviewed `bundlePins` entry or the same chain. Companion snapshots are keyed by bundle hash and verified with authenticated tree receipts before reuse.

In `signed-offers` mode only: build `TargetPath` outputs alone receive the owner's signature. Other executables must match restored NuGet bytes, retain valid Microsoft organization signatures and terminate at a pinned Microsoft root. Unsupported signers, including possible Json.NET dependencies, stop the build for integrator review. `authenticode.json` supplies the manifest's `owner` or `microsoft` signer class; the server rejects executables without a valid class. The agent release must implement both contract amendments before activation.

## Bridge mode

`bridgeMode` is `server-only` (the default), `signed-offers` or `ed25519-offers`; any other value stops the configuration (`BRIDGE_MODE_INVALID`).

- `server-only`: the round deploys the server pair only. It compiles, signs and offers no client bridge, and the vault needs no `authenticodeThumbprint` (`manifestPrivateKey` and `journalKey` stay required). The client bridges are those the currently published agent packs ship: `agentPack` and `agentPackByRuntime["net<N>"]` (by the Studio's .NET major) in the private configuration, cross-checked against the reviewed agent release at `agentReleaseCommit` (on `agentReleaseRef`) with `git show` of four files: the ODC client (a net10 ODC Studio takes `Version` or `EarlierVersion`, a net8 one `EarlierVersion` only), the ODC command lists of the Node and native agents (only what both run) and the ODC bridge project (the Studio assemblies it is compiled against). Every ODC bridge a pack declares (`odcBridge` and `odcBridges`) must be one that release attaches to that runtime; the configuration alone is never trusted. Nothing comes from the server, the environment or a hello. A release that cannot be read (no pin, a commit not in the clone, a missing file) makes the round wait with `agent-release-required`, saying what to configure.
- The new pair's kernel: `odcBridge` is the newest bridge the pack ships for that ODC Studio's runtime; `odcBridgeAccepted` is every published pack's ODC bridge that the reviewed release builds (`Version`, `EarlierVersion`) plus what the nearest served ODC pair accepts (the same version, else the newest below, else the oldest above); `o11BridgeAccepted` is only what the nearest served Service Studio pair accepts (downloaded-bridge protocols `dN`; a pack's `o11Hook` is `dev` or `h1`, never `dN`, so the packs add none).
- The gate, before any bundle, test, build or mutation: each lane of the pair needs a published bridge for its Studio's runtime (the `runtimeconfig.json` of the verified installer; the served bundle for the kept lane), and the hello of the published pack (its real bridges, the release's ODC commands with `reconcile-merge`) must be compatible with the new kernel on both lanes with the window's served versions. The built image is smoked with that same hello, and after deployment the remote check posts it to the new pair. Otherwise the lane waits with `client-bridge-update-required` and the notice `SSAM: client bridge update required` (`client bridge update required: <lane> <version> runtime <tfm> (<reason>)`); production is never touched for that lane. This wait and `agent-release-required` end only when the owner acts, so each also sends a release event `waiting` with the code `CLIENT_BRIDGE_UPDATE_REQUIRED` or `AGENT_RELEASE_REQUIRED`: the local notice, a line `waiting <pair> <CODE>` in the VPS journal (`logger -t ssam-vigia`) and the webhook when `webhookUrl` is in the vault. It is sent once for each new reason (a sha256 of the code and the text), so the same wait is not repeated every round, while a new reason the same day, for the same pair, gives a new event and a new notice (the daily notice key carries the reason). Publish an agent pack whose bridge loads in that Studio, declare it with its reviewed `agentReleaseCommit`, and the next round retries. After `laneWaitHours` the other lane may go alone, as for any deferral. A built image that refuses the hello the gate accepted is a defect (the gate and the image disagree), so that attempt fails with its notice instead of waiting.
- Service Studio: a thin bridge binds to the exact `ServiceStudio.*` versions it was compiled against, so the gate requires the pack's `o11Builds` entry for exactly that Service Studio, with its `runtime` (`{version, runtime}`); it never falls back to the pack's default build, and the post-deploy check refuses a presented hello whose `o11BuiltFor` is not that build. Only a live proof recorded by the owner lets another build serve it, in this exact form: `o11BridgeProven: {"11.55.96": {"studioVersion": "11.55.96", "build": "11.55.94", "packCommit": "<agentReleaseCommit>", "provenAt": "2026-11-08T10:00:00Z", "evidence": "C:/ssam-priv/vigia/proofs/<file>"}}`, with an optional `"sha256"` of the file. `studioVersion` repeats the key; `build` is another o11Builds entry of the pack, built for the Studio's runtime and run by a Service Studio the window serves (the server refuses a hello built for an unserved Studio); `packCommit` is the reviewed `agentReleaseCommit` (a proof of another pack is no proof); `provenAt` is an ISO date-time with its zone, not in the future; `evidence` is a regular file (no link, its real path still) under `C:\ssam-priv\vigia\proofs`, at most 64 MiB. Each round reads the file and its sha256 (a recorded `sha256` must match); free text, an unknown field, a missing or moved file is refused, logged, and the lane that needed it waits with `client-bridge-update-required` and `its o11BridgeProven entry is refused: <why>`. The proof that serves the new pair (studioVersion, build, packCommit, provenAt, evidence, sha256, size) is written to `release.json` (`bridges.o11Proofs`) and the round log, and only that recorded proof, never the configuration, tells the post-deploy check which build the hello may present.
- ODC Studio, a new version: besides the runtime, the release's bridge project references (`<Reference Include="$(OdcInstall)\X.dll">`) are compared by assembly identity with the served ODC Studio of the same .NET major the published bridge already runs in (`odc-binary.mjs`, `odc-references.json` in the attempt). A missing assembly, another name, another public key token, another major version, or a lower version is a gap (`client-bridge-update-required`). It does not prove that the types, members and signatures the bridge calls keep their shape within the same major (OutSystems moves build numbers every release), that the Studio behaves the same, or that the bridge loads and runs there: only a live attach of the published pack proves that. It compares with the served Studio, not with the bridge binary's own references. It compares only the `<Reference Include="$(OdcInstall)\...">` items: a framework assembly the build redirects to the Studio's copy instead (for example `System.Collections.Immutable` through `kernel/Directory.Build.targets` in the kernel, or a `PackageReference` the bridge resolves from the Studio folder) is not in that list, so a change of it in a new Studio is not seen by this check (N5). The served Studio is its frozen bundle (`docker/ssam-server/studio-odc.txt`), which keeps no embedded browser: `WebViewControl.Avalonia`, `Xilium.CefGlue` and `Xilium.CefGlue.Common` are only required to exist in the new Studio's installed folder and are listed as `notCompared`.
- `signed-offers` keeps the round that builds, Authenticode-signs and offers client bridges, with the custody above; it requires the thumbprint.
- `ed25519-offers` (F1 of the agent auto-update plan): the `server-only` gate on the published packs, plus client bridges the round compiles from its verified Studio bundles (`auto-runtime.mjs` `buildBridges`, the same projects and runtime checks as `signed-offers`) right after the bundles, before any test. Nothing is Authenticode-signed and the vault needs no thumbprint: `classify-signers.ps1` only verifies (the `TargetPath` outputs are `owner`; every other dll/exe must be the bytes of a restored NuGet package with a valid Microsoft Corporation code-signing signature that chains, at its signing time and with online revocation, to a root pinned in `publisher-pins.json` both by thumbprint and by SHA-256, the agent's `BRIDGE_MICROSOFT_ROOTS`; an owner entry point never passes as Microsoft; anything else stops the round). The manifest is Ed25519-signed with `manifestPrivateKey` and carries no `authenticodeThumbprint` (the server accepts it absent or null, still refuses any malformed value, and every executable still needs its signer class). The build evidence (local NuGet paths) stays in the attempt folder (`bridge-evidence/`), never in the served stage. The new pair's kernel is the `server-only` kernel plus the offered protocols (`d1` in `o11BridgeAccepted`). The gate (`offersGate`): an ODC gap still waits (the hub offers an ODC bridge only to a refused pack, and the offered protocol has the client's own name); an O11 gap (no thin bridge built for that Service Studio) is closed only when the published pack's hello with `bridgeOffer: true` (app 0.2.8, which accepts Ed25519-only offers) receives this round's signed offer and the same hello with the offer installed is compatible on both lanes, else the lane waits with `client-bridge-update-required`. The image smoke and the post-deploy check post that hello offered and installed, and a hello with `bridgeOffer: false` (agent 0.2.7, empty anchor) must receive no offer; what 0.2.7 gets on the new pair is recorded in `release.json` (`bridges.legacy`) and the round log, and never blocks the round. R7: in this mode the agent release is read, and in both offer modes agent code is compiled, only when `agentReleaseCommit` and the tip of `agentReleaseRef` carry the owner's SSH signature (`ownerSigningPublicKey`, `git verify-commit`); `acceptUnsignedMain` never waives it, and an unsigned release waits with `agent-release-required`.
  F1 review (round 2): (a) the vault manifest key must be the key app 0.2.8 pins: `bridgeTrustKeySpkiSha256` in the private configuration (64 lowercase hex, the SHA-256 of the SPKI DER of the public key, `2ce611d0...d7f0` for today's key) is compared with the key `secrets()` read; a missing pin (`BRIDGE_TRUST_KEY_UNPINNED`) or another key (`BRIDGE_TRUST_KEY_MISMATCH`) stops the round before any build or signature. (b) The new pair's kernel names `o11PackBuiltFor` (its own Service Studio and, when `o11BridgeProven` names a verified proof for it, that build): the hub serves that Service Studio to a hello without an installed signed bridge only through one of those builds; otherwise 0.2.8 gets the offer (`BRIDGE_UPDATE_REQUIRED`) or, with nothing it can install, `AGENT_PACK_MISMATCH` cause `BRIDGE_NOT_INSTALLED`; macOS `BRIDGE_PACK_REQUIRED`; 0.2.7 `AGENT_UPDATE_REQUIRED` (install app 0.2.8), also once the default build leaves the window. The gate and the post-deploy check fail an image whose hub would still answer ok there. (c) A lane whose inputs did not change (recipe, Studio bundle sha256, runtime, protocol, source commit: `agentReleaseCommit` for O11, the signed main for ODC, and the key) is staged with its kept signed manifest and sequence (`<tempRoot>/bridges-signed`), never re-signed n+1; the hub treats an installed later sequence of the offered protocol as active. (d) The post-deploy check sends the offers keyed by pair (`"<o11>|<odc>"`): a retained backend that shares a Studio version is asked none, and the remote verifier requires exactly one backend to report `offersChecked` equal to the offers (`OFFERS_NOT_CHECKED`); every delivered file is compared by sha256. (e) R7 resolves `agentReleaseRef` as the local branch `refs/heads/<ref>` of the vigia-run clone (a tag of the same name is never used): that branch must exist there.
  F1 review (round 3): (a) the rule of (b) is a family rule: on a kernel with `o11PackBuiltFor`, EVERY installed Service Studio (the pair's own, a newer one routed here by its ODC Studio before a pair of its own exists, which the window answers "newer") is served only through a thin bridge built for exactly that build: the pack's own build, a build a verified `o11BridgeProven` proof covers (`o11PackBuiltFor` for the pair's Studio, `o11ProvenBuilds` `{"<studio>": ["<build>"]}` for the others), or a signed bridge installed for it; else the same per-agent refusal. Older Service Studios are refused by this backend as before (`STUDIO_VERSION_MISMATCH`, served by their own pair). The gate and the post-deploy check also ask the legacy hello from the next Service Studio (`nextPatch`). Server-only kernels (no `o11PackBuiltFor`) answer as before. (b) The pin is 64 hex digits in either case (normalized to lower case, as `key-verification.json` prints it upper case); anything else is `BRIDGE_TRUST_KEY_UNPINNED`. The launcher keeps the two pin codes and their message (fingerprint prefixes only) in the console and the Windows notice instead of "Required secrets ... missing"; `--dry-run` in ed25519-offers checks the pin's format (no vault) and stops with exit 2. (c) In ed25519-offers the workspace update also fetches `+refs/heads/<agentReleaseRef>` from `trustedRemote` into `refs/remotes/vigia/<ref>` and moves the local branch R7 reads only to an owner-signed fast-forward (compare-and-swap); an unreachable, unsigned or rewritten line only logs its status (`agent release line <ref>: updated|current|unsigned|diverged|unreachable`) and the rounds that need it wait as before. Activation: the branch must be on `trustedRemote` (or created once in the clone). (d) Sequences never go below the highest one the journaled `release.json` of `outDir` released (a lost `bridge-sequences.json` never signs #1 again). (e) The reuse inputs include `tools`, the SHA-256 of `auto-runtime.mjs`, `classify-signers.ps1` and `authenticode-chain.ps1`. (f) `*.json` of a bridge (runtimeconfig, deps) must be the bytes recorded right after the build.

## Rehearsal without a new Studio

`vigia.ps1 -Config <file> -RehearseCurrent`, as the watcher account, runs the real round on the versions the window already serves: real execution checks and vault, the official installers downloaded and verified, baseline and candidate tests, the image built and smoked; in `signed-offers` mode the bridges are built and signed and asked of that image, in `server-only` mode no bridge is built and the image must accept the published agent pack's hello (`rehearsal.json` records `bridgeMode`, the kernel and the hello's bridges), and in `ed25519-offers` mode the bridges are built with an Ed25519 manifest only, the image must offer them to the published pack's hello and accept that hello with them installed (`rehearsal.json` adds each offer's `signers` counts, `hello.installed`, `offerLanes` and `legacy`, the 0.2.7 result; a manifest naming a thumbprint fails the rehearsal). It stops there. It takes no VPS lock, publishes nothing, pins nothing, backs nothing up, and never PATCHes or deploys. Its only contact with production is one Coolify GET and the SSH `capacity` read: the live snapshot is refused because it issues and revokes a token on the live server. So the window comes from `versions.json` of the checkout, not from the live compose. `PAUSE` refuses it. Receipts (and, in both offer modes, the signed store) stay in `<outDir>/rehearsals/<stamp>`, which no real round reads; its bundles and its `rehearsal-*` image are removed at the end. It takes as long as a real round.

## Deployment and recovery

Live compose, kernels and digests define the baseline. Retained pairs preserve their image identities. New pairs inherit only environment, networks and deployment/resource settings, using generated volumes without inherited bind mounts or extra volumes.

ODC model plugins: every backend mounts the read-only `odc-model-plugins` volume at `/tmp/.local/share/OutSystems/ODC Studio/Plugins` (`compose.template.json`; the kernel children resolve LocalApplicationData from the home of uid 10001, `/tmp`). The files are pinned by name and sha256 in `server/deploy/coolify/model-plugins.json` (MobileUI 1.4.0.0 and 1.5.0.0 today): tenant binaries the owner stages in that volume, never code from a customer. A retained backend deployed before the mount gets it; any other mount at that target, a writable one or a second one stops the round (`MODEL_PLUGINS_CONFLICT`, `MODEL_PLUGINS_MOUNT`). The remote `prepare` accepts only this volume and `runtime-css` outside `/data`, read-only at exactly their targets, never mounts them in its staging container, and refuses before any write unless the plugins volume exists and holds exactly the pinned files (`MODEL_PLUGINS_MISSING`, `MODEL_PLUGINS_MISMATCH`). After a deployment the remote check requires the read-only mount in every running backend and, inside each, the pinned files (`check-backend.mjs`), and in server-only mode exactly one backend presenting the published pack's hello (`PACK_HELLO_NOT_PRESENTED`); a failure rolls back. These remote codes, the failed receipt of a backend check (`CHECK_RECEIPT`), `MODEL_PLUGINS_UNPINNED` and `SERVED_LIST_CHANGED` keep their own code in the deployment journal, the `failed`/`rollback-failed` event (VPS journal line and webhook) and the result (`cause`); only an unknown code becomes `REMOTE_FAILED`. Memory, disk, the lease, a backend still warming and the transport are waits (`MEMORY_LOW`, `DISK_LOW`, `LOCK_BUSY`, `LOCK_LOST`, `NOT_WARM`, `REMOTE_UNAVAILABLE`); the others are failures.

Served lists (`SSAM_SERVED_VERSIONS`): a backend counts a Studio version on its served list but not its own as served elsewhere and refuses it, while the router reaches a pair only through its ODC version. So an older backend must never learn a newer Service Studio: it serves a client of its own ODC version with that newer Service Studio "with the newer note" instead. `versions.json` gives each backend its list (`gen-compose.mjs servedLists`): a pair's own `served` (`{"odc": [...], "o11": [...]}`, the same on its ODC and O11 entry, holding its own versions), else r44's `keepServed: N` (the first N backends share the list of the first N pairs), else the whole window. The rule as the watcher adds a pair: every pair it keeps is written with the list it runs with (from `versions.json`, or from the live compose through the live baseline), the new pair has no `served` and gets the whole new window, and `keepServed` is not carried (once the order changes, only per-pair lists keep its meaning). So a deployed backend's list never changes while it is served; a version that leaves the window may stay on an older backend's list (a client of it gets the served-elsewhere guidance to update, which is what it needs). Before anything is written the recomposition refuses a retained backend whose list would change (`SERVED_LIST_CHANGED`), and after a deployment the remote check requires every running backend to run with the pinned list (`SERVED_LIST_CHANGED`, rolled back). To change an older backend's list on purpose, edit its `served` in `versions.json` and deploy that change by hand outside the watcher.

The window keeps the new pair and the newest served pairs by version (ODC Studio, then Service Studio), whatever their place in `versions.json`: a pair appended by hand is never evicted for being last. Recent real clients can retain a pair for 14 days, up to `maxWindow` (default: the window `versions.json` serves, never below 4; the example sets 5 for a five-pair window, which the rotation, the compose generation, the capacity check and `-RehearseCurrent` support (the multi-backend release rehearsal `coolify/rehearse.mjs` takes five images from the r44 change)). A `maxWindow` below the served window, or retention beyond it, defers and notifies. Exceeding the limit defers and notifies. Verification hellos are marked and excluded, as are revoked tokens and legacy `Version verification` observations. The current token store has no deletion interface for old revoked verification credentials.

Tags include a random attempt suffix. Transient pre-mutation failures persist `deferred` and reuse publication/pin checkpoints on resume. PAUSE, time reserve, available memory and backup disk checks precede mutation.

All actors must take `/var/lock/ssam-release.lock` (manual wrapper: `with-release-lock.sh`). A held lease writes a random `/var/lock/ssam-release.owner` token. Mutations check the token and occupied lock; SSH uses keepalives. Compose is compared before backup/PATCH, then read back and compared with the sent hash before restart. Lost leases are reacquired before rollback; failure to obtain a lease produces `rollback-failed` and an alert.

Rollback uses the original encrypted compose, images, kernels and per-backend budgets. After manually checking/restoring production, the owner can use `-Retry <id> -AcknowledgeRollback <id>`; Retry alone cannot bypass rollback failure. Keep snapshots referenced by live attempts plus the five newest files, and five complete remote backups.

## ODC features (no Studio sign-in per version)

The ODC kernel needs a readable `Features.plain.xml` to initialize the Studio's static feature provider, and the values of the few flags its model-layer assemblies read (six in 1.7.30: AI_NL2Agg, MultiPortfolioOrganizations, UseNewSystemTrackedClipboard, WrapEditCommandsInDelayedVerySlowOperations, FixDragAndDropMultipleElements, FixIconConversionIssues). The model itself answers from the ModelAPI provider compiled into each version and never reads the file. So no ODC version waits for a signed-in Studio.

`featuresRoot` (private, never under `C:\t`; in automatic mode it goes through the same execution-trust `-PrivatePaths` check as the other private paths, a missing one is created only after the other private paths passed it, below one of them (`tempRoot\features` by default), one folder at a time and without following a link or junction; anywhere else it is refused and nothing is created) keeps `odc-<a.b.c>/Features.plain.xml` with `features.provenance.json`, a journal (MAC-signed in automatic mode, bound to its path) with `mode`, `sha256`, the file's `Version`, its `source`, `chain` and the drift. Every use (the round, the tests, the smoke, the remote prepare and -Approve) checks the MAC and the sha256 again; a difference stops the lane with `store-mismatch` and changes nothing. A new folder appears whole (file and provenance staged, then one rename). In automatic mode a folder without provenance is never trusted (`store-mismatch`: review it, delete it by name and seed it again) and the legacy store (`bundleRoot/odc-<v>/Features.plain.xml`) is not used. The modes:

- `exact`: an export of that very version: seeded by the owner, exported from `featuresSource`, or, in manual mode only, a folder of the watcher from before provenance that holds features (recorded as `legacy`) or the legacy store (`legacy-store`). An exact file is never replaced.
- `carried`: a version without its own export gets a byte copy of the nearest exact file (the newest lower version, else the oldest higher one; never a carried file), `chain` counting the versions since that export. Keys whose kind changed in the new version are left out (`filtered`).
- `defaults`: only with `featuresDefaultsFallback: true` (default false) and no exact file anywhere: `<Features Version="<full version>"/>`, the Studio's code defaults alone. Without it the lane waits with `features-unavailable` and the seed instruction.

The drift is static, on the frozen snapshot of the new version (`pe-metadata.mjs`, no .NET run): the catalog of `ServiceStudio.Common.dll` (`FeaturesValues` *Key constants and getter types), the getters the model layer calls (ServiceStudio.BuiltInBehaviors, ServiceStudio.Framework, OutSystems.Model*, Plugins/**/ServiceStudio.Plugin.* and OutSystems.Model.Plugin.*), the new flags (they use the code defaults), unknown keys, kind conflicts and the kernel flags missing. Nothing blocks on drift: the candidate tests and the smoke run the new kernel with that file and stay the gate. PROPOSTA.md, APROVADO.md, attempt.json and release.json name the provenance (no feature values); a carried or defaults-only file gives one notice a day per version, insisting after three versions without an exact export.

`featuresSource` is optional: when it names a cache this Windows user can decrypt, its export becomes the exact file of the version it says (never of another one) and replaces a carried one at the next round. A file that exports to an invalid document stops the lane with `features-invalid`.

Seed the exact exports once, as the watcher account: `vigia.ps1 -Config <config> -SeedFeatures <Features.plain.xml>` (one file per call). It takes the watcher lock, validates the file strictly (at most 1 MiB, UTF-8 without a byte order mark like the export itself, an XML declaration of version 1.0 only at the very start, XML whitespace only (space, tab, CR, LF), no DOCTYPE, ENTITY, entity other than the five of XML or `]]>` in a value: it accepts exactly the documents features-protect.ps1 prepares that follow the features contract, which a seeded differential test checks both ways; root `Features` with a four-part `Version`, `Feature key="GUID" kind="Boolean|Integer|String"`), stores it once as `exact` (over a carried or defaults-only file at most) and prints only the version, the feature count and the sha256.

## Round 4 operational requirements

The scheduled task uses a dedicated clone, never a worktree. Its only supported logon type is Password. Run install-task.ps1 with explicit Config and Workspace; Get-Credential requests that account's password once, passing it to Task Scheduler in memory. Interactive and S4U are refused. No password is written to a file or command log.

Configure absolute paths for node, python, dotnet, git, bash, powershell, tar, docker, sshKeygen and automaticDeployment.ssh.executable. System executables must be in Program Files or System32 and owned/writable only by the trusted OS principals; the executable and its own folder (searched first for DLLs) keep the full rule and every folder above it, up to the drive root, the ancestor rule. Private executables must be owned by the account under C:\ssam-priv. Automatic vigia.ps1 never selects node from USERPROFILE or PATH. Private path descendants and ancestor owners are checked too.

Before resuming a deferred release, observe production again. An already served pair closes the journal as idle. Otherwise recompose retained pairs and repin against the new baseline and CAS hash. By default a journal expires after three deferrals or 48 hours, becomes abandoned with its own `abandoned` notification carrying the last deferral code, and later rounds continue. `-Retry <id>` reopens an abandoned (closed) attempt; an idle closure is served and cannot be reopened. Unchanged closed inputs are not rebuilt; new inputs may run again. Configure maxDeploymentDeferrals/maxDeferredHours only after review.

Extraction is keyed by the installer SHA-256. Its authenticated provenance is checked before reuse, including publisher verification again. keepArtifacts defaults to two unreferenced artifacts per managed group (extractions, bridges, agent sources, snapshots and installersDir installers). Never removed: what unfinished journals reference; the journals of the pairs the live baseline serves (recorded as live-pairs.json each time it is read; before the first read every `live` journal counts); every bundle receipt in bundleRoot with the extraction and installer it cites; the snapshot of each stored bundle; the installer of each extraction kept. Removing a retired bundle from the store frees its extraction, snapshot and installer at the next round. Check free disk before download/extraction. Window size and estimated remote memory are checked before tests or image/bridge compilation.

Certificate paths use the signed countersignature timestamp (classic or RFC3161), explicit online revocation policy and environmental deferral when revocation service is unavailable. The agent must adopt the same timestamp semantics; this repository change does not update it.

Every lock owner records a random token and PID. Both the watcher and manual wrapper use flock with no fork; remote fencing verifies that the live PID owns that inode in /proc/locks. Install the revised manual wrapper before any release.

A deployment records deploySent before requesting restart. A failure before that point restores compose without restarting the existing containers. After reacquiring the lease, rollback accepts only the watcher's compose or the captured baseline; a third writer causes rollback-failed and an alert. Post-PATCH verification compares canonical JSON, tolerating whitespace and object-key ordering only.

Provenance sidecars and snapshot receipts use the journal MAC key. Automatic journal reads without that key are refused. build.sh receives VCS_REF and TAG from the verified runtime and never invokes Git in automatic mode.
